* Goal

Scaffold a new Rust-based CLI tool =nct= (executable =nct=) to eventually
assist with NixOS configuration management in this repo. Companion / eventual
successor-ish to the Python-based =ncf= tool, but starting from a minimal
scaffold.

* Stage 2 — nix-bindings-rust integration + =machine eval-expr=

** Context / investigation

=../nix/nix-bindings-rust/= (reference only).

*** Crate layout (workspace)
- =nix-bindings-util= — version detection (parses =pkg-config --modversion
  nix-store-c=, emits =cfg(nix_at_least="2.26")= etc.), settings, context.
- =nix-bindings-store= — =Store::open=, =StorePath=.
- =nix-bindings-expr= — =EvalState= / =EvalStateBuilder=, =eval_from_string=,
  =require_*= (int/bool/string/list/attrs), =call=, =call_multi=,
  =gc_register_my_thread=, =init=.
- =nix-bindings-flake= — =FlakeSettings= + =EvalStateBuilderExt::flakes=,
  enables =builtins.getFlake= / flake refs in an =EvalState=. Depends on
  =nix-bindings-fetchers= (which needs Nix ≥ 2.29).
- =nix-bindings-fetchers= — =FetchersSettings=; Nix ≥ 2.29.
- =-sys= siblings: bindgen-generated FFI, not for direct use.

*** Build requirements (the hard part)
These are not pure-Rust crates. =build.rs= / =pkg-config= / bindgen need, at
build time:
- Nix's C headers + libraries, discoverable as =nix-store-c= / =nix-expr-c=
  via pkg-config. The version string drives =cfg(nix_at_least=...)=.
- =pkg-config= (nativeBuildInput).
- =libclang= / =clang-unwrapped= for bindgen (=LIBCLANG_PATH=,
  =BINDGEN_EXTRA_CLANG_ARGS=-x c++ -std=c++2a=).
- =stdenv.cc= (for =stdbool.h=).
- With gcc stdenv: the upstream =bindgen-gcc.sh= shim sets
  =NIX_CC_UNWRAPPED= so bindgen finds system headers.

Upstream provides an =nciBuildConfig= flake-parts module for nci users; we use
=rustPlatform.buildRustPackage= (see =modules/nct.nix=), so we must replicate
that config manually as =nativeBuildInputs= / =buildInputs= / env on the
derivation. Reference impl: =../nix/nix-bindings-rust/flake.nix= →
=config.nix-bindings-rust.nciBuildConfig=.

Local Nix version: =2.34.8= (Determinate), so the ≥ 2.29 fetchers floor and
≥ 2.26 =EvalStateBuilder= are both satisfied.

** Playground target

#+begin_src shell
nct machine eval-expr llm-runner 'm: builtins.attrNames m.config.llama-models.configurations'
#+end_src

Semantics (mirrors =nix eval --apply=):
1. Load this flake's =nixosConfigurations.<name>= (full NixOS module eval) as a
   Nix value, via =builtins.getFlake=. <name> is =llm-runner=.
2. Apply the user lambda (=m: ...=) to that value (so =m= is the whole
   =nixosConfigurations.llm-runner= attrset — /note/: this is the *top-level*
   machine attrset, i.e. ={ config, pkgs, ... }= result, so =m.config.X= is the
   right access pattern).
3. Print the result: strings verbatim, lists/attrsets as a JSON-ish dump
   (reuse =nix eval='s output shape where cheap; full pretty-print is a
   follow-up).

A flake ref is needed because the playground reads =.#nixosConfigurations=;
so =EvalState= must be built with flakes enabled
(=EvalStateBuilder::flakes(&flake_settings)=).

* Stage 3 — experiment: adopt nix-cargo-integration (nci)
:PROPERTIES:
:STATUS: DONE
:END:

** Motivation
Stage 2 hand-wired a =rustPlatform.buildRustPackage= derivation for =nct=
and replicated upstream =nix-bindings-rust='s =nciBuildConfig= by hand
(=nixBindingsBuild= attr in =modules/nct.nix=). That works, but:
- The build config (pkg-config / libclang / bindgen args / clangStdenv) is
  duplicated between the package derivation and the dev shell, and maintained
  by us instead of consumed from upstream.
- We lose nci's niceties: automatic per-profile packages (dev/release),
  =check= / =clippy= / =docs= outputs, the crate-aware dev shell, lockfile
  generation app, etc.
- =nix-bindings-rust= *natively targets nci*: it ships an =nciBuildConfig=
  deferred module + an =input-propagation-workaround= that auto-adds the
  correct Nix C libraries (=nix-expr-c=, =nix-store-c=, ...) based on which
  =nix-bindings-*= crates are *direct* deps. Using nci lets us consume that
  instead of reverse-engineering it.

** What nci is
- A [[https://github.com/hercules-ci/flake-parts][flake-parts]] module
  ([[https://github.com/90-008/nix-cargo-integration][90-008/nix-cargo-integration]], checked out at
  =../nix/nix-cargo-integration/=).
- Builds Cargo projects via [[https://github.com/nix-community/dream2nix][dream2nix]]
  (crane-backed), provides a dev shell, and exposes per-crate outputs:
  =config.nci.outputs."<crate>".{packages,devShell,check,clippy,docs}=.
- Config surface (see =../nix/nix-cargo-integration/src/{interface,modules}=):
  - =nci.projects."<name>".path= :: project/workspace root.
  - =nci.crates."<name>"= :: per-crate config (=export=, =profiles=,
    =runtimeLibs=, =drvConfig= / =depsDrvConfig=).
  - =drvConfig= / =depsDrvConfig= :: =attrsOf anything= merged into the
    dream2nix derivation. Shape = { mkDerivation = {...}; env = {...}; }=.
    Set =deps.stdenv = pkgs.clangStdenv= to override stdenv (see
    =examples/customize-stdenv=).
  - =nci.toolchainConfig= / =nci.toolchains.{mkBuild,mkShell}= :: toolchain
    (defaults to =pkgs.rustPlatform= toolchain; rust-overlay optional).

** How =nix-bindings-rust= integrates with nci (=the native support=)
From =../nix/nix-bindings-rust/flake.nix= (=config.nix-bindings-rust=):
- =nixPackage= (default =pkgs.nix=).
- =nciBuildConfig= :: a *deferred module* to import into your crate's
  =drvConfig= / =depsDrvConfig=. It sets:
  - =mkDerivation.buildInputs = [ pkgs.stdenv.cc ]= (stdbool.h).
  - =mkDerivation.nativeBuildInputs = [ pkgs.pkg-config ]=.
  - =mkDerivation.postConfigure= = gcc bindgen shim (only if gcc stdenv).
  - =env.LIBCLANG_PATH=, =env.BINDGEN_EXTRA_CLANG_ARGS = "-x c++ -std=c++2a"=.
- =input-propagation-workaround.nix= :: auto-detects direct =nix-bindings-*=
  deps from the dream lock and adds the matching =nix-*-c= libraries to
  =buildInputs=. Toggle via
  =nix-bindings-rust.inputPropagationWorkaround.enable=.

So with nci + the =nix-bindings-rust= flake-parts module imported, our entire
=nixBindingsBuild= block in =modules/nct.nix= collapses to ~3 lines.

** Consumption pattern in *this* repo (dendritic + flake-file)
This flake is =flake-parts=-based and modules auto-discovered via
=import-tree ./modules=. Inputs are declared per-module through
=flake-file.inputs.<name>= (see =modules/formatter.nix=, =modules/srvos.nix=,
=modules/stylix.nix=) and regenerated with =nix run .#write-flake=. A
flake-parts =flakeModule= input is consumed by =imports = [
inputs.<x>.flakeModule ];= at the top of the module that needs it (e.g.
=modules/formatter.nix= imports =inputs.treefmt-nix.flakeModule=).

=> To adopt nci we add a =flake-file.inputs.nci= (and
=nci.inputs.nixpkgs.follows = "nixpkgs"=) somewhere, then =imports =
[ inputs.nci.flakeModule ]= + nci config in =modules/nct.nix=. We also need
the =nix-bindings-rust= flake-parts *module* (=config.nix-bindings-rust=)
available, which means a *flake input* for =nix-bindings-rust= (not just the
Cargo git dep). Note: =nix-bindings-rust= itself =imports nci=, so its flake
input will transitively pull nci too — we can =follows= them to dedupe.

** Proposed wiring (modules/nct.nix rewrite)
#+begin_src nix
{ self, inputs, ... }:
let
  selfLib = self.lib.self;
in
{
  flake-file.inputs = {
    nci = {
      url = "github:90-008/nix-cargo-integration";
      inputs.nixpkgs.follows = "nixpkgs";
    };
    # For the nciBuildConfig + input-propagation-workaround flake-parts module.
    # (The Cargo crates themselves still come via the git dep in Cargo.toml.)
    nix-bindings-rust = {
      url = "github:nixops4/nix-bindings-rust";
      inputs.nixpkgs.follows = "nixpkgs";
    };
  };

  imports = [
    inputs.nci.flakeModule
    inputs.nix-bindings-rust.modules.flake.basic # -> perSystem.nix-bindings-rust
  ];

  perSystem = { pkgs, config, ... }: {
    nci.projects."nct".path = selfLib.dir' "tools/nct";
    nci.crates."nct" = {
      export = true;  # -> config.nci.outputs."nct".packages.<profile> as flake packages
      depsDrvConfig.deps.stdenv = pkgs.clangStdenv;
      drvConfig = {
        imports = [ config.nix-bindings-rust.nciBuildConfig ];
        deps.stdenv = pkgs.clangStdenv;
      };
    };
  };
}
#+end_src
Then re-export as =packages.nct= / devshell / overlay from
=config.nci.outputs."nct"=, replacing the hand-rolled =packageFn= and
=devShells.nct=.

** Open questions / risks — detailed analysis
:PROPERTIES:
:CUSTOM_ID: stage3-risks
:END:
All three core risks have been *traced through the upstream source* (dream2nix
@ rev =dd8a3eb=, nci source in =../nix/nix-cargo-integration/src/=). Findings:

*** RISK 1 — flake-source leakage via =nci.projects.<n>.path=  (LOW)
:PROPERTIES:
:VERDICT: likely fine, but must verify empirically
:END:
- *What we need:* =nct='s source enters the store as a path whose hash depends
  /only/ on =tools/nct='s contents, so editing unrelated repo files does not
  rebuild =nct= (the repo invariant documented in =modules/flake-packages.nix=
  and enforced by =packages.check-no-flake-source-leak=).
- *How Stage 2 achieves it:* =selfLib.dir' "tools/nct"= evaluates to
  =builtins.path { path = self.outPath + "/tools/nct"; name = ...; }= — an
  *independent* store entry, content-addressed by that subtree.
- *How nci consumes path:* in =src/implementation.nix=,
  =evalCrate= sets =mkDerivation.src = mkForce project.path=, and
  =getProjectCrates.nix= does ="${path}/Cargo.toml"= (string coercion). A
  =builtins.path= coerces to a store path string just fine, and the
  =builtins.path= call (not =self= interpolation) is what governs the hash.
- *The subtlety / the actual risk:* dream2nix's =rust-cargo-lock= translator
  walks the source tree via =prepareSourceTree { source = cfg.source; }= and
  parses *all* =Cargo.toml= + =Cargo.lock= it finds. If =prepareSourceTree=
  materializes the whole =src= path verbatim (it does — it's an opaque tree
  copy), then because =selfLib.dir'="tools/nct"= already narrows to that
  subtree, only =tools/nct= contents matter. /If instead we passed =self= or
  a ="${self}/tools/nct"= string/, leakage would return. So the rule is:
  /keep passing the =builtins.path= (dir'), never a bare-string =self= path./
- *Failure mode if wrong:* =nix build .#nct= rebuilds on every unrelated edit;
  =check-no-flake-source-leak= (already in =devShells.default=) would catch
  it on the nixos-system closure, but =nct= itself is a dev tool not in the
  closure, so we must add a targeted check (see Probe #1).
- *Residual unknown:* whether dream2nix's =getRootSource= / =prepareSourceTree=
  pulls in anything beyond =src= (e.g. parent dirs for workspace resolution).
  =tools/nct= is a single-crate, not a workspace, so workspace-member globbing
  in =getProjectCrates.nix= is a no-op — low risk.

*** RISK 2 — transitive-input weight (dream2nix + crane + rust-overlay?)  (LOW–MED)
:PROPERTIES:
:VERDICT: acceptable; purely a cost, not correctness
:END:
- *New transitive inputs:* =nci= itself pulls =dream2nix=, =crane= (pinned
  =v0.19.0= / =v0.21.1= depending on nci rev), =rust-overlay=, =mk-naked-shell=.
  Note crane is a =flake: false= tarball (see =nci/flake.nix=), so it's a single
  fetch, not a live input. dream2nix is the heavy one (large repo).
- *Plus =nix-bindings-rust= as a flake input* (for the =nciBuildConfig= module)
  pulls its own =nix= + =nci= — but with =inputs.nixpkgs.follows= and nci
  deduped, the marginal cost is just one more lock node.
- *Impact:* larger =flake.lock= (cosmetic), slightly slower *first*
  =nix flake metadata= / =nix develop= (more nodes to fetch). No effect on
  =nix build= wall-time after inputs are cached, and /no/ effect on the
  =nct= derivation itself.
- *Why it's not a blocker:* every other flake-parts consumer in this repo
  (=treefmt-nix=, =stylix=, =clan-core=, =arion=, =direnv-instant=) already
  carries comparable weight. nci is in the same class.
- *Decision:* accept. Optionally measure =nix flake archive --dry-run |
  wc -l= before/after to quantify.

*** RISK 3 — git deps under dream2nix's =rust-crane= backend  (was: biggest unknown → now LOW)
:PROPERTIES:
:VERDICT: resolved by source reading — should "just work" with NO outputHashes
:END:
This was flagged as the biggest unknown. Reading dream2nix's actual vendoring
path resolves it favorably:

- *Pipeline:* =nci= → =dream2nix= =rust-cargo-lock= (parses =Cargo.lock= into
  a =dreamLock=) → =rust-cargo-vendor= (materializes each dep) → =rust-crane=
  (=crane.buildPackage= with =cargoVendorDir= pointing at the vendored tree).
- *How a git dep is parsed:* =translate.nix → parseSourceImpl= recognizes
  =git+<url>?<type>=<value>#<sha>= and emits ={type="git"; value={url; sha;
  type?; value?;};}= into the dreamLock =sources=.
- *How a git dep is fetched:* =lib/internal/fetchers/git/default.nix=,
  =fetched = hash: ...=. The decisive branch:
  #+begin_src nix
  fetched = hash:
    if hash == null
    then if ! refAndRev ? rev
         then throw "Cannot fetch git repo without integrity..."
         else builtins.fetchGit (refAndRev // { inherit url submodules;
               shallow = true; allRefs = ! hasGitRef; })
    else fetchgit (refAndRev // { inherit url; fetchSubmodules = submodules;
               sha256 = hash; });
  #+end_src
  i.e. when there is /no/ hash (the common case for git deps, which carry no
  =sha256= metadata in =Cargo.lock='s =[metadata]= table — only crates.io
  crates get checksums), dream2nix falls back to =builtins.fetchGit= with
  =shallow = true=. This is *precisely* the same primitive our current
  =cargoLock.allowBuiltinFetchGit = true= uses; dream2nix just invokes it
  itself during source materialization rather than letting cargo/nixpkgs do
  it during vendor.
- *Consequence:* the =nix-bindings-*= git deps should resolve with /zero/
  =outputHashes= maintenance — same trust model (content of the git rev) as
  today. The =sha= from =Cargo.lock= pins the rev; =builtins.fetchGit=
  verifies the tree is fetched at that rev.
- *Caveats that could still bite:*
  1. dream2nix rewrites =.cargo/config.toml= (via =writeGitVendorEntries=) to
     point git sources at the vendored dir. If =nix-bindings-rust='s crates
     have *path* deps among themselves (they're a workspace!),
     =replaceRelativePathsWithAbsolute= must rewrite them. The upstream repo
     dogfoods nci on itself, so this path /is/ exercised — but our
     consumption is as a *consuming crate*, not the workspace root, so the
     path-rewrite logic runs against the /fetched/ nix-bindings tree, which is
     intact. Low risk, but Probe #2 confirms.
  2. =builtins.fetchGit= during evaluation = pure eval incompatibility. This
     repo is /not/ evaluated in pure-eval mode for builds, so fine; but if we
     ever run =nix flake check --pure-eval=, git deps without hashes fail.
     Stage 2 has the identical limitation today.

* Stage 4 — =machine provision-pve= (cloud-image + clan age key via cloud-init)

** Goal

A single =nct machine provision-pve <name> -p <proxmox-host>= command that
provisions a *cloud-image-based* VM on Proxmox, with the clan age key for the
machine injected via cloud-init so the custom Stage-1 =provision-clan-key=
initrd unit can bootstrap clan/sops secrets on first boot.

This is the =ncf machine provision-vm= flow, but:
- The disk is a prebuilt qcow2 =cloudImage= (=make-disk-image.nix=, see
  =modules/machines/xray-exit.nix=) instead of disko =diskoImages=.
- Secrets are *clan*-managed: the machine's age private key
  (=sops/secrets/<machine>-age.key=) is decrypted via clan's =SecretStore=
  and planted into the NoCloud =user-data=, not the legacy SSH-host-key-only
  path.

** What =ncf= already does (reference for the =nct= port)

=ncf='s Proxmox interaction is entirely over SSH (no Proxmox API token):
- =ncf/proxmox_api.py= =ProxmoxClient= uses =proxmoxer= with the
  =ssh_paramiko= backend (auth = root SSH keys from =~/.ssh/=). It clears
  =SSH_AUTH_SOCK=/=SSH_AGENT_PID= to dodge paramiko agent bugs.
- =qm= commands are issued by *shelling out to plain =ssh root@<host>=*
  with =shlex.join(remote_cmd)= — NOT via the proxmoxer API. See
  =provision_vm.py ssh_command()= and =provision_vm_anywhere.py=. This is the
  key reuse insight: **we don't need a proxmox client library at all** —
  =ssh root@<host> qm ...= is the whole API surface we touch.
- =upload_snippet()= opens a raw paramiko/SFTP session to write
  =/var/lib/vz/snippets/<file>=. The =nct= equivalent can do the same over
  =ssh ... cat > /var/lib/vz/snippets/<file>= (or =scp=).
- =upload_iso()= streams a file via =pv | ssh root@<host> 'cat > ...'=.

So =nct='s runtime deps for this are minimal: =ssh=, =shlex=-equivalent
shell quoting (we already shell out to =ssh= via =tokio::process::Command=).
No Rust =proxmoxer= equivalent exists/needed. (Optionally =rsync= for the
  qcow2 copy, or =ssh cat >= like ncf's ISO path — ncf uses =rsync -avP= for
  the raw disk in =provision_vm.py= Step 8; we'll mirror that.)

*** The full =provision-vm= flow (=provision_vm.py run())
1. Query NixOS config for metadata: =config.networking.hostName=,
   =config.nixos-config.qemu-guest.proxmox= (memory/cores/bios/disks/
   cloudInit/tpm2/efidisk/...), =config.inventory.hostIpAllocation.<net>=,
   =config.inventory.networks.<net>= (prefix/gateway/vlan/dns).
2. Check VM existence by hostname (=qm list= via the API → for us, =ssh qm
   list= / parse, or =ssh qm config <vmid>= on a guessed id).
3. Build the disk image (=ncf build vm= → =diskoImages=). **We replace
   this with =system.build.cloudImage=**
   (=nixosConfigurations.<name>.config.system.build.cloudImage=, qcow2).
4. Generate cloud-init =user-data= (YAML, =#cloud-config= header) and upload
   as a snippet; wire via =qm create ... --cicustom user=<storage>:snippets/<file>=.
   **This is where we inject the clan age key.**
5. =qm create= with the static =--ipconfig0=, =--net0= (bridge/mac/vlan),
   =--serial0 socket --vga serial0=, =--agent 1=, memory/cores/bios/machine,
   =--scsihw virtio-scsi-single=, optional =--onboot= / =--balloon= / =--shares=.
6. UEFI: =qm set <vmid> --efidisk0 <storage>:1,efitype=4m,pre-enrolled-keys=0|=1=.
7. TPM2 (if enabled): =qm set <vmid> --tpmstate0 <storage>:1,version=v2.0=.
8. Import disk: =rsync= the image to =/tmp/<machine>-disk.qcow2= on the host,
   then =qm set <vmid> --scsi0 <storage>:0,import-from=/tmp/...=, then
   =qm set <vmid> --boot order=scsi0=, then =rm= the temp file.
9. Optionally =start= the VM.

*** The clan age-key injection (the important bit)

The target module =modules/provision-clan-key.nix= defines an initrd systemd
unit =provision-clan-key.service= that, during Stage 1 (after =sysroot.mount=,
before =initrd.target=):
- mounts the NoCloud seed =/dev/disk/by-label/cidata= (iso9660 or vfat),
- greps =^AGE-SECRET-KEY-1= out of the seed's =user-data= file,
- writes it to =/sysroot<secretLocation>/key.txt= (chmod 600),
where =secretLocation = clan.core.vars.age.secretLocation or
"/etc/secret-vars"= (default =/var/lib/sops-nix= per
=clanCore/vars/secret/sops/default.nix=, but =modules/impermanence.nix=
overrides to =/persist/var/lib/sops-nix=).

So the =nct provision-pve= command must:
1. Decrypt the machine's age private key. Source of truth: the sops secret
   =sops/secrets/<machine>-age.key= (a sops-encrypted JSON blob with
   =data= holding the key). Clan decrypts it via =SecretStore.populate_dir=
   (phases =users= → writes =key.txt=). Two implementation options for =nct=:
   - **(A) Shell out to =clan secrets get=** (or clan_lib) — mirrors how the
     value travels at runtime, no reimplementation. This is the =ncf= way
     (=gather_secrets_for_clan_machine= calls clan_lib's =SecretStore=).
     Simplest, stays correct as clan evolves.
   - **(B) Shell out to =sops -d sops/secrets/<machine>-age.key=** and parse
     the JSON =.data= field. More fragile (couples to sops JSON layout);
     avoid unless clan isn't on PATH.
   → Prefer (A): =clan secrets get <machine>-age.key= prints the raw key to
     stdout (it's what =ncf= / clan_lib effectively do under the hood).
2. Embed it in the cloud-init =user-data= as a =write_files= entry, e.g.:
   #+begin_src yaml
   #cloud-config
   write_files:
     - path: /user-data   # not really — see below
   #+end_src
   …except =provision-clan-key= reads the *seed's user-data file directly*
   (the whole NoCloud =user-data=), not a =write_files= target. So the key
   just needs to be a plaintext line in the =user-data= the seed drive
   serves. Simplest: append the bare =AGE-SECRET-KEY-1...= line to the
   =user-data= YAML (cloud-init ignores trailing junk it can't parse as
   cloud-config keys; the grep anchor =^AGE-SECRET-KEY-1= is robust). Or wrap
   it in a =write_files= entry that's also valid YAML — either works because
   the initrd unit only greps. **Decision: append the bare key line at the
   end of user-data** (matches what =provision-clan-key= expects and is
   minimally invasive).
3. Upload =user-data= as a Proxmox snippet and reference via =--cicustom
   user=<storage>:snippets/<machine>-cloud-init.yaml=.

Note: Proxmox's CloudInit drive (=qm set <vmid> --ide0 <storage>:cloudinit=)
provides the =cidata=-labelled NoCloud seed that =provision-clan-key=
mounts. =--cicustom user=...= makes Proxmox bake our =user-data= into that
seed drive. So the wiring is: snippet → =cicustom= → CloudInit drive →
NoCloud seed → initrd grep → =key.txt=. All already designed for this.

*** Config introspection via nix-bindings (NOT =nix eval --json=)

**Decision: use the in-process EvalState (already wired in Stage 2), not
=nix eval= subprocesses, for all config introspection.** Rationale:
- A single =builtins.getFlake= + navigation through one long-lived
  =EvalState= means the full =nixosConfigurations.<name>= module eval is
  computed **once** and memoised in the EvalState's value graph. Every
  subsequent =require_attrs_select= / =require_string= / =require_int=
  reuses the already-forced thunks → near-free. ncf spawns a fresh =nix eval=
  per attribute (=NixRunner.run_eval= × ~6), each re-evaluating the whole
  module system from scratch (or hitting the eval cache, but still
  process-spawn overhead + re-navigation).
- We already pay for the FFI build (Stage 2/3); reusing it for introspection
  is the actual ROI beyond the =eval-expr= playground.
- The API surface we need is tiny and already proven by =eval_flake_apply=:
  =eval_from_string= (getFlake), =require_attrs_select{,_opt}= (navigate),
  =require_string= / =require_int= / =require_bool= / =require_list_strict=
  (extract typed leaves). No serde structs for the whole qemu-guest schema —
  we navigate attrset-by-attrset and build a small Rust =VmConfig= struct by
  hand. This is *more* robust than a big serde derive (schema drift only
  breaks the one field being read, not the whole parse).

Proposed =nix_eval.rs= additions (a long-lived =NixFlake= handle):
#+begin_src rust
pub struct NixFlake {
    es: EvalState,           // GC-registered-thread-owned
    flake_value: Value,      // builtins.getFlake "<root>"
    // thread handle / scope guard so all calls land on the GC thread
}
impl NixFlake {
    pub fn open(flake_root: &str) -> Result<Self>;
    /// Navigate dotted attr path under the flake root, return the Value.
    pub fn attr(&mut self, path: &str) -> Result<Value>;
    /// Convenience: attr + require_string.
    pub fn attr_str(&mut self, path: &str) -> Result<String>;
    pub fn attr_int(&mut self, path: &str) -> Result<i64>;
    pub fn attr_bool(&mut self, path: &str) -> Result<bool>;
    /// Load a whole nixosConfigurations.<name> once; subsequent
    /// config.* reads reuse the forced value.
    pub fn machine_config(&mut self, machine: &str) -> Result<MachineConfig>;
}
#+end_src
The =EvalState= must live on the GC-registered thread (Stage 2 invariant),
so =NixFlake= either owns a dedicated thread + channel, or exposes a
=with_es(|es| ...)= closure API. Simplest: keep the =std::thread::scope=
pattern but hold it open for the process lifetime via a ='static= worker
thread (spawn once in =main=, send closures over a channel). Defer the
exact ergonomics; the point is *one EvalState, many reads*.

*** Cloud-init networking from the chosen network

Since cloud-image VMs have =staticNetwork = false= (systemd-networkd not
wired), cloud-init is the sole network configurator. We generate **two**
cloud-init inputs in sync:
1. A NoCloud =network-config= (v2) snippet, wired via =--cicustom
   network=<snippet-storage>:snippets/<machine>-ci-network.yaml=. This is
   what the guest actually consumes (addresses/routes/nameservers/search).
2. The matching Proxmox-native =--ipconfig0 ip=X/prefix,gw=Y= + =--nameserver=
   for the same values. =--ipconfig0= is reflected in =qm config= / the web
   UI / =qm cloudinit dump=, while =cicustom network= is what lands in the
   NoCloud seed (probe-confirmed: Proxmox bakes =cicustom= files *verbatim*
   into the seed ISO; =ipconfig0= generates Proxmox's *own* network-config
   which =cicustom network= overrides). **Setting both, in sync** keeps
   =qm config= self-documenting for operators while the actual seed comes
   from our v2 snippet (full DNS + search domain, which =ipconfig0='s
   =gw=/nameserver= can't fully express). Belt + suspenders: if they ever
diverge it's a bug, but they won't — both derive from the one inventory
   network the operator passed via =--network=.

If the net has a =vlan=, tag it on the =qm --net0 ...tag=<vlan>= side (host
bridges onto the right VLAN; guest sees untagged eth0).

So the snippet set per VM becomes:
- =<machine>-ci-user.yaml= → =#cloud-config= + authorized_keys + the age
  key under a dedicated =clan-machine-key:= top-level key (see below).
- =<machine>-ci-network.yaml= → Network Config v2 from the chosen inventory
  network.
- =--cicustom user=<snippet-storage>:snippets/<machine>-ci-user.yaml,network=<snippet-storage>:snippets/<machine>-ci-network.yaml=
  + =--ipconfig0= / =--nameserver= mirroring the network values.

* Stage 5 — investigation: inject clan age key directly into the disk image
:PROPERTIES:
:STATUS: IMPLEMENTED (libguestfs path); live validation pending
:END:

** Motivation

The current Stage 4 design (now working end-to-end) ships the clan age key
via a **separate NoCloud cloud-init seed** drive: =nct= uploads a =user-data=
snippet to Proxmox, =qm create ... --cicustom user=...= bakes it into a
CloudInit ISO (label =cidata=), and =modules/provision-clan-key.nix='s initrd
unit mounts that ISO and greps =clan-machine-key:= out of it. That works, but
it carries real operational baggage (all documented in Stage 4's open Qs):
- A second drive (the CloudInit ISO =--ide2 <st>:cloudinit=) must exist and be
  wired, even though its /only/ real payload for this flow is the one key line.
- The initrd must ship =iso9660=/=vfat= kernel modules
  (=boot.initrd.kernelModules=) or =provision-clan-key= can't mount the seed.
- cloud-init itself must be coerced into cooperating on this image
  (=modules/cloud-init-bwrap.nix=, the =updates: {network: {when: [boot]}}=
  gate, the dropped =users-groups= module, ...).
- The seed is a plaintext bearer of the age private key sitting on the
  Proxmox host's snippet storage until the VM is destroyed.

The alternative this section investigates: **bake the age key into the qcow2
disk image itself** at provision time, removing the seed drive, the initrd
fs-module requirement, and cloud-init from the secret-bootstrapping path
entirely. The image is already machine-specific (built per-=-<name>= every
provision run), so embedding a per-machine secret in it is not a portability
regression — unlike a generic AMI where that would be a non-starter.

** The hard constraint: =make-disk-image.nix= cannot take a secret

The qcow2 is produced by
#+begin_src nix
system.build.cloudImage = import "${pkgs.path}/nixos/lib/make-disk-image.nix" {
  inherit lib pkgs config;
  format = "qcow2";
  partitionTableType = "efi";
  additionalSpace = "1024M";
};
#+end_src
=make-disk-image.nix= (in =../nix/nixpkgs/nixos/lib/make-disk-image.nix=)
offers two hooks that look relevant and are /both/ traps for secrets:
- =contents= :: =[{source, target, mode, user, group}]=. But =source= is
  interpolated verbatim into the builder bash array
  (=sources_=(${lib.concatStringsSep " " sources})=, line ~470) and =rsync=-ed
  into the image root. A nix string is a store path or gets copied /into/ the
  store first → the age key lands world-readable in =/nix/store=. **Hard no.**
- =postVM= :: shell code run after the VM finishes installing. It /could/
  =dd= a secret onto the image, but it's evaluated inside the nix derivation,
  so any secret it references is again in the store / drv env. Same leak.
- =additionalPaths= :: more store paths. Not for secrets.

=> The key /cannot/ enter the image through the nix build. It must be
   injected **after** the pure nix-built qcow2 is materialized, as a impure
   post-processing step on the build host (the machine running =nct=). This is
   the same trust boundary as =clan secrets get= today: the secret lives on
   the operator's machine, never in the nix store.

** The three injection mechanisms (all post-build, all impure)

The qcow2 is a real disk image with an ext4 root labeled =nixos= (per
=modules/machines/xray-exit.nix= =fileSystems."/"=) and a vfat =ESP=. After
=nix build= materializes =<store>/nixos.qcow2=, =nct= can:

*** Option A — =libguestfs= (=guestfish=) to write the file in-image
- Tool: =guestfish --rw -a nixos.qcow2 -i write /var/lib/sops-nix/key.txt <key=
  (=virt-customize= / =virt-copy-in= are wrappers over the same libguestfs).
- Pros: no host root needed, no mount, handles qcow2 + LVM + UEFI ESP
  natively, single tool, well-trodden path (it's what cloud image base
  customization flows use everywhere).
- Cons: pulls =libguestfs= as an =nct= runtime dep (nixpkgs has it:
  =pkgs.libguestfs=, ~tens of MB + a temporary appliance VM per invocation).
  Slower than a raw mount (boots a micro-VM to manipulate the fs) — but this
  runs /once per provision/, not in a hot loop, so fine.
- Secret handling: =guestfish= reads the key from =nct='s process memory (a
  pipe / temp file with =chmod 600=, unlinked immediately), writes it into the
  image, =chmod 600=. Never touches the nix store.

*** Option B — =qemu-nbd= + =mount= (loop-mount the qcow2)
- Tool: =modprobe nbd=; =qemu-nbd --connect=/dev/nbd0 nixos.qcow2=;
  =mount /dev/nbd0p2 /mnt=; write =/mnt/var/lib/sops-nix/key.txt=; =umount=;
  =qemu-nbd --disconnect=.
- Pros: no extra package beyond =qemu= (already implied by the toolchain);
  fast (direct kernel mount, no appliance VM).
- Cons: **requires root on the build host** (=nbd= + =mount=), which the
  operator running =nct= may not have / want to escalate to. Partition index
  discovery (=nbd0p2= vs =p1=) is image-dependent and brittle. =nbd= module
  may not be loaded. Leftover mounts on failure.
- Secret handling: same as A (temp file → mount → write → shred).

*** Option C — =debugfs -w= (ext4 direct, no mount)
- Tool: =debugfs -w /dev/nbd0p2= then =write temp_key /var/lib/sops-nix/key.txt=
  (=debugfs= can operate on an unmounted ext4, even inside a qcow2 via nbd).
- Pros: no =mount=, no root-for-mount (still needs nbd connect → still root).
  Survives a dirty fs better than a full mount.
- Cons: same root/nbd requirement as B; =debugfs write= is low-level and
  fiddly for setting perms/mtime; rarely used for this in the wild.

*** Verdict on mechanism
- **Prefer A (=libguestfs=)** as the default: no root, robust across image
  layouts, single self-contained dep, the standard tool for exactly this job.
- Keep B as a documented fallback for hosts where =libguestfs='s appliance
  boot is problematic (nested-virt-disabled build hosts, air-gapped).
- Skip C (no advantage over B, more fiddly).

** Where the key lands in the image

The destination is the /same/ path =provision-clan-key= currently writes to,
so the downstream consumers (clan's sops machinery, =sops-install-secrets=)
are identical and need no changes:
- =clan.core.vars.settings.secretStore == "sops"= →
  =''${clan.core.vars.sops.secretUploadDirectory}/key.txt= =
  =/var/lib/sops-nix/key.txt= (the resolved value already encoded in
  =modules/provision-clan-key.nix='s =secretLocation= logic).
- So =nct= writes =AGE-SECRET-KEY-1...\n= to =/var/lib/sops-nix/key.txt=
  (mode 0600, owner root) inside the image, via the chosen mechanism.
This is the exact invariant =provision-clan-key= enforces; we're just moving
the write from initrd-time to build-time and dropping the seed drive entirely.

** What gets removed / simplified if we switch

- =modules/provision-clan-key.nix= :: the whole initrd unit, the =iso9660=/
  =vfat= =kernelModules= additions, the mount/umount/cleanup dance, the
  =clan-machine-key= grep — **all deletable**. The module can either be
  dropped or reduced to a no-op guard (or kept only for non-=provision-pve=
  provisioning paths that still use a seed).
- =modules/cloud-init-bwrap.nix= :: **may still be needed for networking**
  (cloud-init's =network-config= v2 path is what configures eth0; that's
  independent of the age key). This stage is /only/ about removing cloud-init
  from the /secret/ path. If networking is later baked into the image too
  (Stage 4 open-Q option B), cloud-init could go away entirely — but that's
  out of scope here.
- =nct='s =cloud_init::user_data= :: drops the =clan-machine-key:= line and
  the =updates: {network: {when: [boot]}}= gate is /still needed/ for
  networking. So =user-data= shrinks but the snippet upload step stays.
- =qm create= args :: the =--cicustom user=...= half goes away (keep
  =--cicustom network=...=). The =--ide2 <st>:cloudinit= drive /can/ stay
  (it's what serves =network-config=) or be replaced by a plain NoCloud seed
  — but keeping the CloudInit drive just for networking is fine and matches
  the current working setup.

  *Net:* the seed drive stops carrying a secret; it (or a slimmer equivalent)
  may remain for networking only. The initrd secret-extraction complexity is
  gone entirely.

  without hardcoding =/var/lib/sops-nix=. Add it to the one-shot =toJSON=
  lambda.

** Trade-offs vs the current (cloud-init seed) design

| Aspect                     | Seed drive (now)              | Baked into image (proposed)        |
|---------------------------+-------------------------------+------------------------------------|
| Extra Proxmox drive        | CloudInit ISO (carries key)   | CloudInit ISO for net only, or none |
| Initrd fs modules          | iso9660/vfat required         | Not needed                         |
| cloud-init on secret path  | Yes (grep from user-data)     | No                                 |
| Secret location on host    | snippet storage (plaintext)   | Nowhere (lives only in qcow2)      |
| Build-host privilege       | None                          | None with libguestfs; root w/ nbd  |
| New runtime dep            | (none)                        | libguestfs (or qemu-nbd)           |
| Key rotation / re-key      | Re-upload snippet, reboot     | Rebuild image                      |
| Reuse-image fast iteration | Trivial (snippet is separate) | Must re-inject per build           |
| Portability of image       | Image is secret-free          | Image embeds a secret (per-machine) |

The last two rows are the real costs. =--test-reuse-image= already implies a
rebuilt-image invariant; baking the key in means reusing an old image re-uses
an old key (fine if the key hasn't rotated, a silent footgun if it has —
=nct= should refuse =--test-reuse-image= when injecting, or warn loudly).
Portability is a non-issue here because the image is =nixosConfigurations.<name>=
specific already.

** STATUS: implementation DONE (libguestfs path), live validation pending

The Option A (libguestfs/`guestfish`) path is implemented and verified against
a real =xray-exit= cloud image via an =#[ignore]d= integration test
(=inject_into_real_cloud_image=, ~28s, passes). Q1's measurement is in: a
single inject is ~25s of guestfish appliance boot + <2s of actual fs work —
acceptable for a once-per-provision step. No nested-virt issue (KVM available).

Key findings baked into the implementation (not predicted by the plan):
- **Do NOT use guestfish =-i= (inspector).** It fails on NixOS cloud images
  ("no operating system was found on this disk") even though the filesystems
  are perfectly mountable. Instead: =run=, =list-filesystems=, pick the ext4
  partition as the root, =mount= explicitly. (=find_root_device= scans
  =list-filesystems= output for the ext4 entry; fails loudly if none.)
- **guestfish argv mode needs =:= separators between commands.** Bare words
  are treated as args to the previous command, so =run list-filesystems=
  fails (=run= a.k.a. =launch= takes no args). =run_guestfish= now takes a
  =&[&[&str]]= (slice of command-slices) and inserts =:= between them.
- **The qcow2 + its workdir must be world-readable (0644 / 0755).**
  guestfish's qemu appliance drops privileges to a different user for
  security; a 0600 image in a 0700 =/tmp= workdir = appliance can't open the
  image = opaque crash. The qcow2 holds no secret in its own bytes (the key
  lives inside its filesystem, readable only post-mount), so 0644 is fine;
  the injected key file inside is still =chmod 0600=.
- **Use =libguestfs-with-appliance=, not =libguestfs=.** Plain =libguestfs=
  lacks the supermin appliance =guestfish= needs to boot its helper VM. The
  =-with-appliance= variant bundles it; its =lib/guestfs/= is what
  =guestfish= auto-discovers (no =LIBGUESTFS_PATH= needed).
- **The injected image is persisted to a named tempfile in =/tmp=, not next
  to the source.** The source is a read-only nix store path; the injected
  copy must live in a writable location for =rsync= to pick up. =inject_age_key=
  returns that path; =provision-pve= rsyncs it onward.
- **Secret hygiene:** the age key is staged in a =tempfile= (0600) and passed
  to guestfish via =upload <tempfile>= (not =write <content>=), so it never
  appears in =guestfish='s argv / process listings.

** Motivation

=xray-front= is the repo's one EC2-hosted machine. Today it is a *manual*
AWS workflow: build the configuration, somehow get a disk onto EC2, launch
an instance, then =clan machines update xray-front --target-host root@<dns>=.
None of that "somehow" is captured in tooling — it's the last machine with
no =nct= (or =ncf=) provision path. Stage 4 gave Proxmox VMs a one-shot
=nct machine provision-pve=; this stage is the AWS analogue, and it splits
cleanly into two sub-commands because AWS *forces* that split:

- =nct machine build-aws-image <name>= — a pure-ish nix build that produces
  an importable AMI artifact (a VHD), with *no* AWS credentials required.
- =nct machine provision-aws <name>= — the impure, credentials-bearing step
  that imports the VHD as an AMI and launches (or replaces) an instance,
  almost certainly via opentofu.

Splitting them mirrors how the AWS image pipeline actually works (build
locally → upload → register AMI → run) and lets the expensive, cacheable,
credential-free build happen in CI / on any builder, while the cheap,
stateful, credential-bearing provision is an explicit operator action.

** Why the split is mandatory on AWS (vs Proxmox)

Proxmox =provision-pve= could fold build + provision into one command
because Proxmox import is =qm set --scsi0 <st>:0,import-from=<local file>=
— a single host-local call against a file we just =rsync='d over. AWS has
no such primitive:

- The disk artifact must be uploaded to S3 as a *VHD* (AWS's =vpc= format),
  then =aws ec2 import-snapshot= (a VM Import Service *job* that polls for
  minutes), then =aws ec2 register-image= against the resulting snapshot to
  get an AMI id. None of that is a single RPC; it's a stateful workflow.
- That workflow needs AWS credentials *and* an S3 bucket *and* a service
  role with the VM Import trust policy (=vmimport=). Building the VHD does
  not. Conflating them would mean =nix build= requires live AWS creds,
  which breaks CI and every offline rebuild.
- The instance itself is best modelled declaratively (instance type, subnet,
  security group, EBS volume, elastic IP, SSH key) — i.e. as *infrastructure
  as code*. Hand-rolling =aws ec2 run-instances= JSON in Rust reimplements a
  worse terraform. opentofu is the right tool for the instance half.

=> =build-aws-image= is nix + a thin =nct= wrapper; =provision-aws= is
   opentofu all the way down.

** Part A — =nct machine build-aws-image <name>=

*** What nixpkgs gives us for free

The EC2 image story in nixpkgs is *not* =make-disk-image.nix= called by hand
(which is what xray-exit's cloudImage does for Proxmox). There is a dedicated,
supported module:

- =nixos/modules/virtualisation/amazon-image.nix= (=../nix/nixpkgs/...=) ::
  the EC2 *config* module. Imports =ec2-data.nix= (applies instance user-data
  SSH host keys) + =amazon-init.nix= (optionally rebuilds from user-data) and
  sets up nvme/ena/xen kernel modules, =ttyS0= console, growPartition, the
  =fetch-ec2-metadata= service, amazon-ssm-agent, =amazon-ec2-utils= udev
  rules, and the right =boot.loader.grub= UEFI/BIOS wiring.
- =nixos/maintainers/scripts/ec2/amazon-image.nix= :: the EC2 *image builder*
  module. Imports the config module above + =disk-size-option.nix= +
  =image/file-options.nix=, and defines =config.system.build.amazonImage=
  via =make-disk-image.nix= with =format = "vpc"= (VHD),
  =partitionTableType = "efi"= (or =legacy+gpt=), =fsType = "ext4"=, and a
  =postVM= that emits =nix-support/image-info.json= with =boot_mode=,
  =logical_bytes=, =system_version=, and the disk file path.

So unlike the Proxmox =cloudImage= (a hand-rolled =make-disk-image= call),
the AWS path has a first-class =system.build.amazonImage= output that already
knows how to be an AMI. nixpkgs' own =release.nix= builds its public AMIs
*exactly* this way (the =amazonImage= attr, ~line 330).

*** What xray-front needs to import

Today =modules/machines/xray-front.nix= hand-rolls the EC2 specifics
(=nvme=/=ena=/=xen_blkfront= modules, =ttyS0= console, DHCP networking,
UEFI-on-EBS, growPartition). Most of that is *duplicated* by
=amazon-image.nix=. The clean conversion (part of the =nixos-base= work in
=todo/xray-front-nixos-base.org=, or a follow-up) is to import the nixpkgs
EC2 module instead and delete the hand-rolled block. For =build-aws-image=
the machine module *must* evaluate with the EC2 image-builder module
imported, or =system.build.amazonImage= won't exist.

*** Networking: plain DHCP via systemd-networkd (NOT cloud-init, NOT baked-in static)

:REQUIREMENT:
The EC2 instance gets its IP/gateway/DNS by sending a DHCP request on
its primary NIC at boot; AWS's hypervisor-side DHCP server assigns them
from the subnet's range. The guest just needs to DHCP on =en*= — *nothing
else*, and emphatically *not* cloud-init's network renderer.
:END:

This is the deliberate design for =xray-front= and it sharply simplifies
the AMI vs the Proxmox cloud-image story. Key points:

- *EC2 networking is real DHCP at the hypervisor level.* Unlike NoCloud
  (Stage 4's Proxmox path), where there is no DHCP server and the network
  config has to be rendered from a static =network-config= v2 seed, EC2's
  virtual network actually serves a DHCP server that hands out the
  subnet-assigned IP, default gateway, and DNS. The guest does not need to
  query IMDS for networking, does not need a network-config file, and does
  not need cloud-init's =NetworkdActivator= at all. A plain
  =systemd-network= DHCP stanza is the complete solution.
- *What xray-front does today is already correct:*
  #+begin_src nix
  networking.useDHCP = false;
  systemd.network.networks."10-ec2" = {
    matchConfig.Name = "en*";
    networkConfig.DHCP = "yes";
  };
  #+end_src
  Keep this verbatim in the conversion. (The =matchConfig.Name = "en*"=
  is deliberately loose because the EC2 NIC name varies by instance
  family — =ens5= / =eth0= / =enX0= — and DHCP-by-name glob is robust to
  all of them.)
- *cloud-init's networking path is irrelevant here.* The entire Stage 4
  saga (NoCloud's =boot-new-instance= network-apply gate, the
  =updates: {network: {when: [boot]}}= knob, the =/usr/sbin= / =/bin=
  hardcoded-path bug that forced =modules/cloud-init-bwrap.nix=, the
  =NetworkdActivator= =.skip-network= failure) was a NoCloud problem.
  None of it touches EC2, because on EC2 cloud-init is not in the network
  path at all — systemd-networkd brings up the NIC via DHCP directly. So:
  - =services.cloud-init.network.enable= stays =false= (the nixpkgs
    default) — do *not* enable it.
  - =modules/cloud-init-bwrap.nix= is *not* needed for the EC2 AMI.
    (Generalising it stays a Proxmox-only concern; it should not be
    imported into the EC2 image.)
  - cloud-init itself may still be useful on EC2 for non-networking tasks
    (authorized_keys from user-data, growing the filesystem), but it is
    optional, not required for bring-up. The =amazon-image.nix= module
    does *not* enable cloud-init — it ships its own =apply-ec2-data=
    service for SSH host keys + hostname, and =fetch-ec2-metadata= for
    metadata harvest. So we may not enable cloud-init on xray-front at
    all; decide during the conversion.

*Bottom line:* the EC2 AMI is *simpler* than the Proxmox cloud image on
the networking axis. No cloud-init networking, no bwrap, no static config
in the image, no per-subnet baking — just DHCP. The IP is assigned at
launch by the subnet and learned dynamically by the guest.

*** Interaction with clan-managed SSH host keys (no conflict, but trim =apply-ec2-data=)

:QUESTION:
Does nixpkgs' =apply-ec2-data= / =fetch-ec2-metadata= (shipped by
=amazon-image.nix=) conflict with clan, which decrypts the SSH host key
from an age-key-protected var into =/run/secrets/...= automatically?
:END:

Reading both sides: **no real conflict on the host key**, but the EC2
services are mostly dead weight on a clan-managed machine and one piece
(=authorized_keys=) does tread on clan's toes. Detail:

- *Clan's host-key wiring is path-based, not =/etc/ssh=-based.* The clan
  =sshd= service (see =../nix/clan-core/clanServices/sshd/default.nix=)
  sets =services.openssh.hostKeys = [{ path =
  <clan-var-path>; type = "ed25519"; }]=, where =<clan-var-path>= is the
  decrypted clan var (=config.clan.core.vars.generators.openssh.files."ssh.id_ed25519".path=,
  i.e. something under =/run/secrets/vars/openssh/=). sshd's resulting
  =HostKey <clan-var-path>= directive means sshd reads the key from the
  clan var, *not* from =/etc/ssh/ssh_host_ed25519_key=.
- *=apply-ec2-data= writes to =/etc/ssh/=, which sshd ignores.* The EC2
  service (see =../nix/nixpkgs/nixos/modules/virtualisation/ec2-data.nix=)
  greps =SSH_HOST_ED25519_KEY:= markers out of EC2 user-data and writes
  them to =/etc/ssh/ssh_host_ed25519_key= (guarded by =if [ ! -e ... ]=).
  Since sshd's =HostKey= points at the clan var path, the file
  =apply-ec2-data= writes is simply never read. **Harmless dead weight**,*
  /provided/ our EC2 user-data doesn't carry those markers — and it won't,
  because we are not putting host keys in user-data (Stage 5 bakes the age
  key into the image; clan generates + deploys the host key itself).
- *=sshd-keygen= self-skips via =ConditionFileNotEmpty=.* nixpkgs'
  =sshd-keygen= service has =unitConfig.ConditionFileNotEmpty = map (k:
  "|!${k.path}") cfg.hostKeys= — the =|!= means "skip the unit if the file
  exists and is non-empty". Because =cfg.hostKeys[0].path= is the clan
  var, once clan's sops decryption has landed it, =sshd-keygen= doesn't
  even run. So there is no "who generates the host key first" race that
  matters: clan wins by virtue of owning the =HostKey= path, and
  =sshd-keygen= defers.
- *The one real toe-step: =authorized_keys=.* =apply-ec2-data= also does
  =cat /etc/ec2-metadata/public-keys-0-openssh-key >> /root/.ssh/authorized_keys=
  (guarded by =if ! [ -e /root/.ssh/authorized_keys ]=). On a clan-managed
  machine, =root='s authorized_keys come from the clan =sshd= service
  instance (=binarin-admin= in =nixos-base=), materialised via the =sshd=
  NixOS module — not from =/root/.ssh/authorized_keys= on disk (NixOS
  sshd doesn't even read that file by default; it uses
  =users.users.root.openssh.authorizedKeys=). So this half of
  =apply-ec2-data= is also inert, but it's the half most likely to
  surprise someone debugging "why does root have an extra key" if the
  NixOS sshd config ever changes.

*Decision for xray-front:* leave =amazon-image.nix= imported as-is (it's
the supported EC2 module and the services are inert on a clan-managed
machine), but **disable the two EC2 services explicitly** to make the
intent unambiguous and to avoid the dead =/etc/ssh/ssh_host_*_key= files
lying around on a system whose real host key lives in a clan var:
#+begin_src nix
# Clan owns the SSH host key (decrypted from a vars generator) and root's
# authorized_keys (via the `sshd` service instance). nixpkgs' EC2 services
# that do the same job from EC2 user-data / metadata are therefore inert
# here; disable them so they don't write dead files to /etc/ssh and so the
# system's secret model has exactly one source of truth.
systemd.services.apply-ec2-data.enable = false;
systemd.services.fetch-ec2-metadata.enable = lib.mkForce false;
#+end_src
(=fetch-ec2-metadata= is also only useful for the hostname + SSH key path
that clan replaces; if we ever want EC2 instance tags / IAM metadata for
something else, re-enable selectively.)

*Net:* clan's host-key management is the single source of truth; the age
key baked into the image (Stage 5) is what lets clan decrypt it on first
boot; the nixpkgs EC2 metadata services are redundant and get disabled.
The only EC2-specific bring-up that actually matters on xray-front is the
DHCP network stanza (above) and =boot.growPartition= (already on).

Two ways to wire it, decision deferred:
- *(A) Permanent import in the machine module.* xray-front always imports
  =amazon-image.nix= (it /is/ an EC2 machine). Then =build-aws-image= is
  literally =nix build '.#nixosConfigurations.xray-front.config.system.build.amazonImage'=
  + reading =<out>/nix-support/image-info.json=. Pro: zero special-casing.
  Con: pulls the EC2 image-builder module into every eval of xray-front
  (including =clan vars=, =nixosConfigurations= for deploy). Probably fine —
  it's cheap.
- *(B) =build-aws-image= extends modules.* =nct= evaluates the machine with
  an extra =[ (modulesPath + "/maintainers/scripts/ec2/amazon-image.nix") ]=
  via =extendModules=, like =ncf build vm= does for disko images. Pro: the
  machine module stays deploy-only. Con: another =extendModules= eval path
  to maintain; mirrors what =ncf='s =build_vm= already does and =nct=
  deliberately wants to move away from (Stage 2's in-process eval is the
  ROI).

→ Lean (A): the EC2-ness is intrinsic to xray-front, import the module
  permanently, delete the hand-rolled EC2 block, and =build-aws-image=
  becomes a thin =nix build= + =image-info.json= reader. (This depends on / is
  adjacent to the =nixos-base= conversion in =todo/xray-front-nixos-base.org=.)

** Part B — =nct machine provision-aws <name>= (opentofu)

*** Why opentofu (not raw =aws= CLI calls, not pulumi, not CDK)

- *Raw =aws ec2= calls in Rust* would reimplement: snapshot import polling,
  AMI registration with the right block-device mapping, the =vmimport= role
  + trust policy, the instance + EBS + ENI + EIP + SG + subnet wiring, and
  *state tracking* (is this run a create or an in-place update? has the AMI
  changed? do we replace the instance?). That state tracking *is* what
  terraform/opentofu is. Reimplementing it is a known tar pit.
- *opentofu* is the license-safe terraform fork (BSL → MPL). Its =aws=
  provider covers EC2 AMI import (=aws_ec2_import_image= / the older
  =aws_ami_from_instance=) and the full instance lifecycle. State lives in a
  =tfstate= we can commit or remote-backend. Drift detection + plan/apply is
  free.
- *pulumi / CDK* add a runtime (a language VM) for no gain here — our
  infrastructure surface is ~6 resources and static. HCL is fine.

*** The AMI-import gap (the one place opentofu's aws provider is weak)

The awkward part: getting our nix-built VHD *into* AWS as an AMI. The AWS
=aws ec2 import-snapshot= API is a long-running *job* (poll until
=completed=) that reads the VHD from S3. opentofu's =aws= provider has
limited first-class support for this:

- =aws_ec2_import_image= resource (newer) :: imports a VM *as an AMI*
  directly. Takes =disk_container = { s3 = { ... } }=. This is the closest
  fit: it yields an AMI id usable by =aws_instance=.
- =aws_snapshot_import= + =aws_ami= (compose) :: import as snapshot, then
  register an AMI from it. More moving parts, more control (block device
  mapping, boot mode).

Both are *job-based* resources — apply can take minutes and the resource is
  not idempotent across VHD content changes without a =triggers= hash. =nct=
  will likely need to:
  1. =aws s3 cp= the VHD to =s3://<bucket>/<name>-<nix-store-hash>.vhd=
     (content-addressed so re-uploads are skipped by S3 iff the hash matches).
  2. Feed that S3 key into the opentofu =aws_ec2_import_image= resource,
     with =triggers = { vhd_hash = "..." }= so a new image forces a re-import.

Alternatively (simpler, less pure): =nct= does the S3 upload +
=import-snapshot= + =register-image= dance itself via the =aws= CLI, writes
the resulting AMI id to a =tfvars= file, and opentofu only manages the
*instance* (which references =var.ami_id=). This keeps opentofu's state
small and fast (no multi-minute import job inside =tofu apply=) at the cost
of a bit of Rust/CLI glue. **Decision deferred** — needs a probe of how
=aws_ec2_import_image= behaves in practice (does =tofu plan= block on the
job? does =tofu apply= re-run it every time or respect =triggers=?).

*** Proposed layout

#+begin_src
tools/nct/aws/                 # new, generated/rendered at provision time
  terraform/
    main.tf                    # provider + instance + eip + sg + key
    variables.tf               # ami_id, instance_type, subnet, ...
    outputs.tf                 # instance_id, public_ip, ...
  tofu.tfvars.tmpl             # rendered from machine config + CLI flags
#+end_src
The HCL is small enough to ship as a template rendered by =nct= from the
machine's =config= (instance type, region, SSH key name, security group
rules from =networking.firewall.allowedTCPPorts=) — mirroring how
=provision-pve= renders =qm= args from =MachineConfig=.

*** CLI surface (proposed)

#+begin_src
nct machine provision-aws <name>
  --region <aws-region>           # required
  --instance-type t3.micro        # required (no silent default)
  --ami <id|latest-built>         # default: the AMI id from the last
                                  #   build-aws-image run (read from a
                                  #   local state file / tfvars)
  --key-name <ec2-keypair-name>   # SSH keypair registered in AWS
  [--subnet-id ...] [--security-group ...]
  [--elastic-ip]                  # allocate + associate an EIP
  [--replace]                     # terminate + recreate the instance
  [--import-image]                # run the S3+import-snapshot+register
                                  #   dance before the instance step
  [--dry-run]                     # tofu plan only / print the dance
#+end_src
Behaviour (sketch):
1. Load =MachineConfig= via the =NixFlake= handle (reuse Stage 4's typed
   loader) for =networking.firewall.allowedTCPPorts=, =networking.hostName=,
   authorized keys (for the EC2 keypair or a cloud-init user-data).
2. If =--import-image=: =nix build ... amazonImage= (or reuse a path passed
   via =--ami-vhd=), =aws s3 cp= the VHD to the content-addressed S3 key,
   run the import-snapshot/register-image job, capture the AMI id.
3. Render =aws/terraform/*.tf= + =tofu.tfvars= from the machine config +
   flags.
4. =tofu init && tofu apply= in =tools/nct/aws/terraform=.
5. Print the instance's public DNS (the value the operator then passes to
   =clan machines update xray-front --target-host root@<that dns>=).

** Credentials / runtime deps

- =build-aws-image=: none beyond =nix= (pure build). No AWS SDK in =nct=.
- =provision-aws=: =aws= CLI (for S3 + the import job if we go that route),
  =opentofu=, and standard AWS env vars (=AWS_PROFILE= / =AWS_ACCESS_KEY_ID=
  / region). Like =provision-pve= (which assumes =ssh=/=rsync=/=clan= on
  PATH), =provision-aws= assumes =aws= + =tofu= on PATH — wrap them into the
  =nct= package via =makeWrapper= (=modules/nct.nix=) when it stabilises.
  No Rust AWS SDK (=aws-sdk-rust= is heavy and would couple us to a
  tokio/rustc version); the CLI is the boundary, exactly as =provision-pve=
  treats =ssh= as the boundary.

** Relationship to the clan age-key injection (Stage 5)

=xray-front= is an EC2 machine, so it boots from an AMI, not a Proxmox
qcow2. Stage 5's =inject_age_key= (guestfish) applies *verbatim* to the
VHD/amazonImage output too — it's a qcow2/vhd with an ext4 root either way.
So =build-aws-image= should gain an =--inject-key= step that writes
=/var/lib/sops-nix/key.txt= into the VHD before upload, exactly as
=provision-pve= does before =rsync=. The AMI then carries the baked-in key,
the instance boots with it, clan's sops machinery decrypts on first boot,
and *no* user-data secret channel is needed on EC2 at all — and on EC2 this
is not just a convenience but a *security requirement*: EC2 user-data is
readable via the IMDS proxy (=http://169.254.169.254/latest/user-data=)
unless IMDSv2 + hop-limit is enforced, so it must never carry the age key.
(See the "Security" subsection under Part A for the full argument.)

** Open questions

1. *State backend for opentofu.* Commit =tfstate= to the repo (simple,
   leaks instance ids but this is a personal infra repo), or use S3 + DynamoDB
   remote state (proper, more setup)? Lean: commit locally for the first cut.
2. *AMI cleanup / garbage collection.* Each =build-aws-image= + import makes
   a new AMI + snapshot; old ones accumulate and cost money. =nct= should
   either deregister old AMIs or at least list them. Out of scope for v1.
3. *Elastic IP vs DHCP.* xray-front's deploy comment says "the EC2 public
   address is not committed" — implying today it's a fresh DHCP address per
   launch. An EIP (=--elastic-ip=) would give a stable deploy target and
   stable =clan.inventory.machines.xray-front.deploy.targetHost=. Decide
   whether to make EIP the default.
4. *Keypair management.* EC2 needs an SSH keypair for the instance. Do we
   reuse an existing keypair by name (=--key-name=), or have =provision-aws=
   create one from the inventory's secure public keys (like =provision-pve=
   bakes authorized_keys into user-data)? EC2 keypairs are a per-region AWS
   object, not per-instance, so a managed =nixos-config-<region>= keypair
   created on first provision is reasonable.
5. *Region / account discovery.* Hardcode via =--region=, or read from a
   machine-level =config.nixos-config.aws= options block (instance type,
   region, key name)? A new =aws= options submodule (mirroring
   =qemu-guest.proxmox=) is the clean long-term home; defer to v2.
6. *cloud-init vs the nixpkgs EC2 services.* Confirmed by reading
   =amazon-image.nix=: it ships =apply-ec2-data= (SSH host keys + hostname
   from =/etc/ec2-metadata=) and =fetch-ec2-data= (harvests IMDS to
   =/etc/ec2-metadata/=), but does *not* enable =services.cloud-init=. So
   the decision to skip cloud-init on xray-front is consistent with what
   nixpkgs’ own EC2 module assumes. Nothing to re-confirm; just don’t add
   =services.cloud-init.enable = true=.
7. *cloud-init-bwrap stays Proxmox-only.* The Stage 4 =cloud-init-bwrap.nix=
   module exists to paper over NoCloud + cloud-init’s hardcoded =/usr/sbin=
   path bug. Since the EC2 image drops cloud-init entirely, this module is
   not imported and does not need generalising. (If we ever want cloud-init
   on EC2 for some future feature, revisit then.)
