* Design choices
** SL-80 guest oom_score_adj
- Single source: =/usr/local/sbin/pve-oom-priority= (run as =python3 -I=)
  imports the deployed daemon =/usr/local/sbin/pve-memguard= with
  =SourceFileLoader= (the import has no side effects: =mlockall=, the
  writer thread and argv parsing only run from =main()=; bytecode writing
  is off so no =__pycache__= appears in =/usr/local/sbin=). It builds the
  effective config with the daemon's own =Config= from
  =/etc/pve-memguard/config.json= (missing file: =Config({})=). The order
  is not copied anywhere. Tests import the sibling =pve_memguard.py=.
- Mapping: =kill_order= is least important first; =d= = index of the
  default tier, =n_below= = number of tiers after it.
  - tier =i < d=: =round(1000*(d-i)/d)= (first tier +1000)
  - default tier and unlisted guests: 0
  - tier =j > d=: =round(-750*(j-d)/n_below)= (last tier -750)
  - default tier first: no positive values; default last: no negative
    ones; only one tier: everything 0. Python =round()= (ties to even).
  -750 stays above the -900 of the host services and never reaches -1000
  (unkillable): postgres (CT 101) stays killable as a last resort
  (binarin's decision).
  With today's order: 123=1000, 111=667, 116=333, default 0, 124=-150,
  vm109=-300, 112=-450, 115=-600, 101=-750.
- Floors (review finding, redesign of the positive tiers): a write to
  =/proc/<pid>/oom_score_adj= by a process with effective
  =CAP_SYS_RESOURCE= also sets its =oom_score_adj_min=, inherited by its
  children; below it, a write without the capability (anything in an
  unprivileged CT) gets EACCES (=linux-v7.0/fs/proc/base.c:1150-1153,
  1174-1175=). Container engines write the OCI spec's =oom_score_adj=
  (0 by default) and abort on failure (runc
  =libcontainer/nsenter/nsexec.c:300-307=, crun
  =src/libcrun/linux.c:5383-5396=). CTs 111 and 116 run Docker and CT 123
  runs podman, all in positive tiers, so a positive floor would break
  them. Rule: a value < 0 is written with a floor (harmless: engines
  write 0, which is above it), a value >= 0 without one. One helper,
  =Host.write_oom_score_adj(pid, value, floor)= with =floor = value < 0=,
  used by =apply=, =hook= and =lxc-start-host=. Without a floor it clears
  =CAP_SYS_RESOURCE= from the effective set for the write (capget/capset
  via ctypes, =_LINUX_CAPABILITY_VERSION_3=; kept in the permitted set and
  restored; =CAP_DAC_OVERRIDE=, needed for CT-owned =/proc= files, stays).
  An error from capget/capset (dropping or restoring) propagates: no
  write is better than a positive floor. Only an EACCES from the write
  itself (the process already has a higher minimum, e.g. inherited from a
  parent; this tool never floors a value >= 0) leads to a two-step write:
  0 with a floor (minimum = 0), then the value without one.
- Trade-off: processes in a positive-tier CT that set a lower value
  themselves (an engine's 0, systemd's =user@= +100) go below the CT's
  value. =apply= raises them again when it runs; =check= lists them as
  "below target (allowed, no floor)" without counting them as problems.
- CTs: =lxc.proc.*= keys are not allowed in a pct config, =lxc.include= is.
  =sync= writes =/etc/lxc/oom-priority/<id>.conf= for every CT config in
  =/etc/pve/lxc=, listed or not, because a missing include file blocks the
  CT start. Files of removed CTs are left alone. Atomic write (temp file +
  fsync + rename), only when the content differs. Content after a comment
  header (CT, tier, value):
  - value < 0: =lxc.proc.oom_score_adj = N=. lxc writes it as host root
    before the CT init execs, so it is also the floor of the whole CT: CT
    processes can raise it, not lower it (EACCES; systemd inside the CT
    ignores that for e.g. udevd's -1000).
  - value 0: nothing else.
  - value > 0: =lxc.hook.start-host = /usr/local/libexec/pve-oom-priority-lxc-hook=.
    lxc runs start-host hooks in the host namespaces after setting
    =LXC_PID= (the CT init's host PID) and before it wakes the init; a
    failing hook aborts the start (=lxc/src/lxc/start.c:1969, 2105-2109=).
    PVE does not set =lxc.hook.version=, so version 0 also passes
    =NAME lxc start-host= as arguments; =LXC_NAME= is set too
    (=start.c:980=). The wrapper (sh, installed by Ansible) runs
    =pve-oom-priority lxc-start-host "$@" 2>&1 | logger -t
    pve-oom-priority-lxc-hook || true= and then =exit 0=: lxc logs hook
    output at DEBUG only, so errors go to syslog. The subcommand writes N
    to =LXC_PID= without a floor and also returns 0 on any error.
- =include <vmid>...= (hand step) adds =lxc.include: /etc/lxc/oom-priority/<id>.conf=
  at the end of the main section, i.e. before the first line starting with
  =[= (snapshot or =[pve:pending]=): a line below a section header belongs
  to that snapshot and is ignored at start. Idempotent (an existing line
  counts in both forms pct parses, =key: value= and =key = value=);
  refuses all CTs (changes nothing) if any CT config or include file is
  missing or a config has a =lock:= property (backup, snapshot, migrate);
  prints a
  unified diff; holds pve-container's config lock
  (=/run/lock/lxc/pve-config-<id>.lock=) and writes via =<file>.tmp.<pid>=
  + rename like PVE's =file_set_contents= on pmxcfs. Not run by Ansible.
- VMs: hookscript snippet =/var/lib/vz/snippets/oom-priority-hook.sh=
  runs =pve-oom-priority hook <vmid> <phase> || true= and then =exit 0=
  (no =exec=: a missing or broken tool must not fail =pre-start=, which
  aborts the start); on =post-start= the tool writes the value to the kvm
  PID (=/var/run/qemu-server/<id>.pid=, accepted only if
  =/proc/<pid>/cgroup= is the VM's =qemu.slice/<id>.scope=). The tool
  also returns 0 on any error; its output goes to syslog
  (=logger -t pve-oom-priority-hook=).
  Only one hookscript per guest: binarin sets it
  by hand after checking none is set. CTs do not use a hookscript (CT 116
  already has =pve-impermanence-hook.pl=).
- =apply= (live, running guests): CT = every PID in =cgroup.procs= under
  =/sys/fs/cgroup/lxc/<id>/= recursively (=lxc.monitor/<id>= is a separate
  tree, not touched); VM = the kvm PID. Per process, emulating a restart:
  write the target if the current value is 0 or below the target,
  otherwise keep it (Docker, chromium at 300). Floor per the rule above.
  Vanished PIDs (ENOENT/ESRCH) are skipped.
- Limitation of the 0 rule: =/proc= does not show =oom_score_adj_min=, so
  0 is taken as "never set". A process that sets 0 on purpose in a CT
  with a negative value (allowed, 0 is above the floor; e.g. a Docker
  container) is set back to the target by every =apply=, which then
  reports a change on every deploy.
- =check= (read-only, exit 1 on any problem): include file content
  (positive: the start-host hook line; negative: the proc key; 0:
  neither), include line in each CT's main section, every running guest's
  processes >= target (in positive CTs only a note, see the trade-off),
  the CT init (the process whose =NSpid= has exactly
  two PIDs, the second 1; nested container inits have more) and the kvm
  PID settled per the =apply= rule, VM =hookscript:= equals
  =local:snippets/oom-priority-hook.sh=, the snippet file is executable
  when VMs exist (a VM whose hookscript file is missing fails to start),
  and the start-host wrapper is executable when any include file names it
  (a missing wrapper blocks the CT start).
- Output: =sync=, =include=, =apply= end with =changed: N= (with
  =--check=: would change); Ansible's =changed_when= compares the last
  line.
** SL-79 ARC cap
- =lineinfile= on =/etc/modprobe.d/zfs.conf= (created if missing, regexp
  =^options zfs zfs_arc_max==) so other options survive; notifies the
  shared =ansible/handlers/update-initramfs.yaml= handler (imported in the
  play's =handlers:=, =update-initramfs -u -k all=; root is on ZFS).
- Live: read =/sys/module/zfs/parameters/zfs_arc_max=; if it differs,
  write the value. In check mode the task runs (=check_mode: false=) as
  =true=, so it reports changed and writes nothing.
- pve-memguard counts ARC above =c_min= as headroom, so the cap lowers its
  headroom figure by whatever the ARC held above 8 GiB.
** SL-82 host OOMScoreAdjust
- Units: pve-cluster and corosync at -900. Deviation from the brief: not
  ssh. sshd (OpenSSH =port-linux.c=, from memory of the review, not in
  =reference/=) saves its starting value, sets the listener to -1000
  itself and writes the saved value back in every session child. With
  =OOMScoreAdjust=-900= every ssh session, and whatever is started from
  it (Ansible modules, manual =vzdump=, =qm start=), would run at -900,
  below every guest, and the live write would lower the listener from
  -1000 to -900. The rollback removes an ssh drop-in in case one was ever
  deployed.
- Drop-ins =/etc/systemd/system/<unit>.d/50-oom-score-adjust.conf= with
  =[Service] OOMScoreAdjust=-900=, =daemon-reload= when one changed.
  Unit -> value map in =vars/memory.yml= (=pve_host_oom_score_adjust=).
- No restart. Live: for each active unit, write -900 to every PID in its
  =ControlGroup='s =cgroup.procs= whose value differs (check mode: only
  report). Inactive units are skipped. Changed only when something was
  (or in check mode would be) written.

* Open / risks
- =pct exec= / =pct enter=: lxc-attach applies =lxc.proc.*= from the CT's
  generated config (=lxc/src/lxc/attach.c:1719-1722=). PVE regenerates
  =/var/lib/lxc/<id>/config= at CT start and on any =pct set= of a
  running CT (=API2/LXC/Config.pm:272=), so after either, attached
  processes in a CT with a negative value get its value and floor. Before
  that, and in CTs with value 0 or a positive value (the start-host hook
  does not run on attach), they keep the caller's value: =check= reports
  it (as a note in positive CTs), =apply= fixes it.
- Processes in positive-tier CTs that lower themselves (engines' 0,
  =user@= +100) stay below the CT value until the next =apply=. Possible
  follow-up: a periodic =apply= (systemd timer). Not done.
- The start-host hook path is not exercised on a PVE host yet, nor that
  the kernel sets no minimum without effective =CAP_SYS_RESOURCE=: see
  "First check of the start-host hook" below.
- A snapshot rollback restores the snapshot's raw lxc keys and drops the
  include line if the snapshot predates it; =check= reports it, re-run
  =include=.
- Live values from =apply= are only a floor for the processes that exist;
  CT processes forked later inherit from their parents, so that holds.
